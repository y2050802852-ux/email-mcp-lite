# 定时发送邮件设计

## 目标

为 email-mcp-lite 增加可跨 ZCode 会话运行的定时邮件能力。用户通过 MCP 安排和管理任务；本机后台调度服务负责在计划时间发送。

## 用户决策

- 采用混合模式：MCP 负责创建和管理任务，独立后台调度器负责执行。
- 第一版以 macOS `launchd` 系统服务安装器为目标，提供安装、卸载、状态查询等命令。调度进程作为独立 CLI 子命令运行。
- 时间使用带 UTC 偏移的 ISO 8601 时间戳，例如 `2026-11-13T09:00:00+08:00`。存储统一转换为 UTC，同时保留原始时区/偏移供展示。
- 任务支持自动发送与到期后等待人工确认两种模式。人工确认任务到期后进入等待状态，MCP 重新连接时可列出并确认；未确认任务不自动发送或过期。
- 任务、邮件内容与状态保存在本机 SQLite 数据库，放在凭证目录（默认 `~/.email-mcp`），数据库权限限制为当前用户。
- MCP 支持创建、列表、编辑、取消、确认发送、重试失败任务。发送中或终态任务不可编辑；取消只对尚未开始发送的任务有效。
- 服务恢复时，若自动发送任务已错过计划时间，则标记为 `missed`，不自动补发。等待确认任务进入 `awaiting_confirmation`。
- 明确可判断为发送前失败的任务标记为 `failed`。SMTP 发送阶段发生连接中断等无法判断是否已被服务器接受的情况，标记为 `unknown`，不自动重试。用户核实后可明确重试。

## 架构与数据流

新增独立调度模块使用 SQLite 作为持久队列，并调用项目现有邮件适配器发送。MCP 工具只负责校验输入和修改任务记录，不在 ZCode 的 MCP 进程内等待计划时间。macOS launchd 在用户登录会话中启动调度器；调度器周期性领取到期任务，并以数据库事务将状态从 `scheduled` 原子转换为 `sending`，避免两个调度进程重复领取。

新建任务时，MCP 保存账户 ID、收件人、抄送、主题、正文、附件路径、计划 UTC 时间、原始时间偏移、发送模式、状态及时间戳。附件只保存路径，不复制附件内容；发送前检查路径可读。任务内容本机明文保存，数据库权限应为 `0600`，所在目录 `0700`，文档明确提醒不得同步或提交该目录。

调度器发送时重新读取当前账户配置，因此账户凭证仍只存在于既有凭证文件。任务到期时，自动模式执行发送；确认模式置为 `awaiting_confirmation`。确认调用会立即执行发送，而不是重新等待一个计划时间。发送完成记录 `sent` 和实际完成时间。`failed` 可由用户显式重试；`unknown` 也仅可在用户明确确认后重试，并在响应中说明重复发送可能性。

## MCP 接口

新增工具：

- `schedule_email(account, to, send_at, subject, body, cc="", attachments=None, mode="auto")`：创建任务。`send_at` 必须是未来的 ISO 8601 时间戳且带偏移。响应回显任务 ID、收件人、主题、计划时间和模式。
- `list_scheduled_emails(status="", limit=50)`：按需过滤并列出任务摘要，不返回正文或凭证。
- `edit_scheduled_email(task_id, send_at=None, to=None, cc=None, subject=None, body=None, attachments=None, mode=None)`：只编辑尚未到期且处于 `scheduled` 状态的任务；更新内容完整校验。
- `cancel_scheduled_email(task_id)`：取消尚未进入 `sending` 的任务。
- `confirm_scheduled_email(task_id)`：发送一条 `awaiting_confirmation` 任务。
- `retry_scheduled_email(task_id)`：用户明确要求后，将 `failed` 或 `unknown` 任务重新排入当前时间可执行队列；`unknown` 响应须警示重复发送可能性。

工具 schema 与命名需兼容项目现有 FastMCP 风格；每个状态变更返回任务当前状态。只读模式开启时，创建、编辑、取消、确认和重试均拒绝执行。

## 状态与失败处理

状态集合：`scheduled`、`awaiting_confirmation`、`sending`、`sent`、`failed`、`unknown`、`missed`、`cancelled`。状态迁移由存储层集中校验。对于过期的 `scheduled` 任务，调度器启动时标记 `missed`；不进行追赶发送。后台服务停止后，任务记录保留，服务恢复后按此规则处理。

通过发送状态写入和单任务锁避免并发重复调度。`sending` 状态遗留（进程在发送阶段崩溃）无法证明远端是否接受邮件，因此恢复时置为 `unknown`，不自动重发。系统不承诺 SMTP 的恰好一次投递。

## 服务管理与安全

增加 CLI 子命令管理 launchd 用户级服务：安装、卸载、查看状态；同时提供前台运行调度器的命令供调试。launchd 配置使用当前 Python/uv 安装的稳定可执行路径，并将日志写入用户应用支持目录。服务安装器不得自动上传数据或联系外部服务。

数据库仅绑定本机用户文件系统，不开网络端口。调度器并发锁和数据库事务保护任务状态。收件人、主题和任务状态可在列表中查看，但正文不出现在列表结果。现有账户凭证不复制到任务数据库。用户通过创建任务明确授权定时发送；等待确认模式要求再次调用确认工具。

## 测试策略

- SQLite 层：建库权限、任务持久化、状态迁移、并发领取、取消/编辑边界、重启恢复时 `missed` 与遗留 `sending` 转 `unknown`。
- MCP 层：参数校验、带偏移时间解析、过去时间拒绝、只读模式、列表脱敏、确认/重试规则。
- 调度器：使用可注入时钟和 fake adapter 验证到期发送、确认等待、发送前失败、SMTP 结果未知、重启处理；测试不连真实邮箱。
- launchd 安装器：用临时目录验证 plist 内容、安装/卸载幂等性和路径转义；不在测试机实际注册系统服务。
- 文档：补充 ZCode 工具说明、服务安装和启动步骤、状态含义、限制、版本变更记录。
